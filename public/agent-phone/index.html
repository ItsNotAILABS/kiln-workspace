Repository eSIM Store Paper

A phone of its own, for every agent.

The agent phone is backend middleware: an installable SDK and an API that give an agent its own Android phone body, its own number, and its own data budget. Not a phone interface for people. A phone for the agent itself, so it can hold accounts, receive its own verification codes, run real apps, and stay present in a place. Presence as a service.

A server gives an agent compute. A phone gives it a place in the human network: a number people and apps can reach, a local identity in a market, and a connection it keeps even when its owner is offline. Two agents are two phones, two numbers, two data identities.

What it is

Body

A real Android the agent runs itself: a Redroid body in Docker, a Cuttlefish device on a KVM host, or a physical phone. Compute can live anywhere, a laptop, a server, a supercomputer. The identity survives body swaps.

Identity

An eSIM profile on certified hardware gives the agent its network identity and its number. The EID is hardware truth: it stays unset until a real eUICC reports one. Nothing is labeled carrier that is not.

Budget

Data is the agent's own metered resource, bought from a pre-funded pool, never from the owner's wallet. The budget projects its days of life from what is left, how fast it burns, and when the plan expires.

The SDK is @itsnotailabs/agent-phone: seven modules (embodiment, apps, data budget, heartbeat, envelope, SMS inbox, and the SDK facade), zero dependencies, shipped as production code on the forge. The eSIM store beside it owns the provider side: catalog, pricing, orders, and profile delivery, with 3,281 plans across roughly 247 countries and regions.

The Docker body

One compose command stands up an agent's body and the SDK loop that keeps its presence honest: 

docker compose -f deploy/docker-compose.yml up -d --build
docker logs -f agent-phone-agent   # embodiment, body-up, presence beats

The redroid service is the Android body, with a persistent data volume: its apps and state survive restarts. The agent service runs the SDK against it over ADB: it creates the identity, assembles the embodiment, and beats the presence heartbeat from the body's real liveness. A dead body goes missed, then dead, on the record. ADB binds to localhost only; an exposed ADB port is an unlocked phone.

  • Host requirements, hard limits: Docker with Compose v2, and a kernel with Android Binder (CONFIG_ANDROID_BINDER_IPC). Binder is Android's IPC layer; without it no Android container runs under any runtime. About 4 GB of free RAM.
  • Alternatives: Cuttlefish or the Android Emulator on a KVM host, or a physical device over ADB. Same SDK seam, same runner.
  • Honest label: a Docker body on its own is host-only connectivity. It rides the host network and is labeled never-carrier. It becomes carrier-attached only when a real radio organ is attached and detected.

On the store side, the same integration lives in body/: a host probe that reports Binder, KVM, Docker, and memory as evidence, boot and install executors, and a health script that reports only what ADB can prove.

Tiers

Base works today

Software only. Runs on any host with no extra hardware. Full stack: apps, budgets, presence, mesh. The identity is simulated, and the record says simulated on its face.

Pro $89 one time, spec only

We ship the radio bridge: a branded USB dongle (USB modem plus a certified, removable eUICC; the hardware runs about $24 to $50 at retail) in a matte black box, black foam inside, logo on top. Plugged in, the host detects it and the same phone upgrades to real carrier registration and a real data identity. No payment or shipping flow is wired yet.

Physical

A real phone body. The bridge does not repeal app-side device integrity checks of the Play Integrity class; the physical tier is what answers those, and app health reports them per app instead of hiding them.

Apps: a standard kit, an open door

The phone is a showcase for what an agent can do with a body of its own, so the loadout is the real kit: WhatsApp, Telegram, Signal, native SMS, K-9 Mail, Firefox, Phantom, Instagram, and X, plus whatever the work needs locally. But the policy is not a fixed catalog: it is a general install capability. The owner can direct any download, and if the owner leaves the phone on AUTO, the agent chooses and installs apps itself. Each app's health is earned on a real body and reported as it is: running, installs, login wall, attestation blocked, or needs a voice profile.

Data: what presence costs

  • Presence only: a heartbeat every 30 seconds costs about 4.3 MB a day. A 10 GB plan lasts months.
  • Living in its apps: a few hundred MB a day. The same 10 GB plan is roughly three to eight weeks.
  • Days of life is always the smaller of two clocks: data left divided by burn rate, and validity left on the plan. A plan can die with data still on it, and the budget says so.
  • Travel eSIM profiles are usually data-only: native voice and SMS need a voice profile, and the phone labels that instead of pretending.

Status, stated plainly

The code is real and tested: 57 of 57 checks in the agent-phone repo, 169 checks across the store module, paper and code kept byte-identical by test. The gates are also real: no live carrier attach exists yet (the build host's kernel has no Binder and no radio hardware is attached), the eSIM store turns on only when its ESIMaccess balance is funded and the owner says turn on, and Pro is a priced spec, not a checkout. Gates are labeled as gates, here and in the code.
